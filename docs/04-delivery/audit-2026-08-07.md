# Project audit — 2026-08-07

## Outcome

The repository is mechanically healthy, but it was not ready to progress because its delivery
documents described three different projects: a completed livestock-and-crops phase, a PowerSync
architecture that was not installed, and a payroll phase with conflicting numbers. The active
branch also carried a 1,839-line handoff whose repeated review transcripts obscured the next action.

This audit establishes one executable sequence:

`livestock → offline sync → crops → labour → finance/compliance → hardening/pilot`

The next engineering phase is therefore **Phase 3 offline sync**, after Phase 2 receives the
owner-triggered review passes required to close its regulated work.

## Scope and evidence

The audit covered the repository entry points, project memory, delivery plan, requirements,
architecture, compliance ledger, contributor guidance, package/build configuration, database
invariants, browser persistence boundary, API and web test suites, e2e harness, and committed-file
hygiene. The repository contains 286 TypeScript/TSX/MJS files, 87 test/spec files, 37 Markdown
documents and 21 SQL migrations at the time of the audit.

Evidence collected:

- Uncached `pnpm verify`: 84 test files and 952 tests passed; all seven packages built; gzipped JS
  was 147.77 KB against a 250 KB budget.
- Browser e2e baseline: 27/27 passed. A final rerun after harness cleanup is recorded in STATUS.
- Database invariant tests assert tenant columns, tombstones and real-Postgres RLS behaviour.
- Static scan found no application hard `DELETE FROM` or ORM delete calls.
- Static scan confirmed the client uses browser-local stores and has no PowerSync dependency.
- `pnpm test:trace` names 40 of 146 requirements. It is intentionally report-only, so this is a
  visibility metric rather than a completion claim.

This is not a substitute for the specialist compliance, sync-tenancy or phase-gate reviews. Those
agents are owner-triggered under `AGENTS.md`, and no such pass was run during this audit.

## Invariant review

- **Offline:** Phase 2 capture paths write locally and have offline behaviour tests. Storage is
  capacity-limited browser JSON, not the promised replication layer; Phase 3 must migrate queued
  data without loss.
- **Tenancy:** schema tests and real-Postgres integration tests cover `farm_id` and RLS. PowerSync
  rules do not yet exist, so cross-device tenancy cannot be cleared until Phase 3.
- **Deletion/audit:** domain tables use tombstones and the application scan found no hard database
  deletion path. Authentication ceremony/session records are documented exceptions.
- **Money and regulated values:** existing domain boundaries use cents and effective-dated reference
  data. The compliance register still contains deployment-blocking `CITED`/`PLACEHOLDER` rows for
  future payroll. No regulated production seed was changed here.
- **Errors:** raw `Error` throws found in production are configuration, provider/context invariant,
  crypto-envelope or framework-boundary failures; domain behaviour continues to use typed errors.
- **Build/release:** local verification is green. The branch is not CI-verified until it is pushed;
  this audit does not push or mark the draft PR ready.

## Progression gate

Before Phase 3 starts:

1. The owner decides the object-storage phase.
2. The owner triggers the Phase 2 reviewer, sync-auditor and compliance-checker if Phase 2 is to be
   declared merge-ready; findings are fixed and re-verified.
3. The branch is pushed and both CI lanes are read before the draft PR is marked ready.
4. Phase 3 begins from the offline-sync checklist, with schema/RLS/sync-rule changes kept in small
   reviewable slices and upgrade tests protecting every existing queued capture.

Do not begin crops or payroll on the browser-local adapter. That would multiply migration risk and
recreate the same review loop this audit is intended to stop.
